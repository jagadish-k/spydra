# ADR-0021 — Drizzle for the BFF's database access

**Status:** Accepted · 2026-10-15
**Context:** phase 0 · affects spec 010, spec 011, `AGENTS.md`

---

## Context

The `ui` schema is four tables. The tempting answer is no ORM at all —
hand-written SQL via `postgres` or `pg`, and a small migration runner — on the
grounds that a library would be more code than it saves.

Two things make that the wrong trade here:

1. **"A plain SQL migration runner" is unbuilt work.** Up/down, ordering,
   a ledger table, a dirty-state guard, and tests for all of it. That is a
   day of writing a worse version of something that exists.
2. **Hand-written SQL in a strict-TypeScript service has no type boundary.**
   A query returns `unknown[]` and someone casts it. Nothing fails at compile
   time when a column is renamed — it fails at 3am in a schedule fire.

Drizzle resolves both: schema in TypeScript, types inferred from it, and
`drizzle-kit` generates and applies migrations.

## Decision

**The BFF uses Drizzle ORM for the `ui` schema, and Drizzle's introspected
types — nothing else — for reading `crawl`.**

### 1. `ui` is Drizzle's, fully

Schema defined in `bff/src/db/schema/ui.ts`. Migrations generated by
`drizzle-kit generate` into `bff/drizzle/`, applied by `drizzle-kit migrate`.

### 2. `crawl` is read-only and **generated, never hand-written**

The BFF has `SELECT` on `crawl` and no write access (spec 010 §3). Alembic
owns that schema.

Hand-writing Drizzle table definitions for `crawl` would create a second
source of truth that silently drifts from the Python migrations. So:

```sh
make drizzle-pull     # drizzle-kit pull --schema-filter crawl
                      # → bff/src/db/schema/crawl.generated.ts
```

The generated file is committed, carries a do-not-edit banner, and
**`make check` regenerates it and fails on a diff** — exactly the rule that
already governs `schema.crawler.d.ts` (ADR-0013). An Alembic migration that
changes `crawl` therefore breaks the BFF build until someone re-pulls, which
is the correct moment to find out.

### 3. `generate` + `migrate`. Never `push`.

`drizzle-kit push` diffs the live database against the schema and applies the
difference with no migration file. It is excellent for a prototype and wrong
here: there is no artifact to review, no down path, and no way to reproduce
the sequence on a fresh database. `make migrate-down` is part of the test
suite (spec 001 §4) and `push` cannot satisfy it.

**`drizzle-kit push` is a defect in this repository.** The pre-commit hook
rejects it in a committed script or package script.

### 4. Drizzle may not write to `crawl`

Enforced in three places, because one is not enough:

| Layer | Guard |
| --- | --- |
| Postgres | the `spydra_bff` role has `SELECT` only (spec 010 §3) |
| Drizzle config | `schemaFilter: ["ui"]` in `drizzle.config.ts`, so generate never emits `crawl` DDL |
| CI | a test asserts every file in `bff/drizzle/` mentions only `ui.` |

The database grant is the real boundary. The other two exist so the failure
arrives at generate time rather than at 2am in a migration.

### 5. Raw SQL where the query is the point

The aggregation in `/api/ui/overview` crosses two schemas and computes a
health series. Drizzle's `sql` template is used there, with an explicitly
declared row type. **This mirrors ADR-0014 on the Python side** — SQLAlchemy
Core for the boring CRUD, hand-written SQL where the query carries the
meaning. Two services, same principle.

## Consequences

**What this costs.**

- A dependency and its migration tooling in a service with four tables.
- `crawl.generated.ts` is a build artifact in version control — the same
  irritation as generated API types, and the same justification.
- Drizzle's own API changes faster than `pg` does. Pin it; it is one more
  thing on the ADR-0017 version-policy list.

**What to watch for.** If the BFF ends up with Drizzle relations, query
builders and a repository layer over four tables, the "more code than it
saves" objection was right after all. Re-read this ADR at the
end of phase 3 alongside the BFF thinness tripwire (ADR-0015) — the two
questions are related, and if the tier collapses this ADR goes with it.

## Alternatives rejected

| Option | Why not |
| --- | --- |
| `postgres` + hand-written SQL (the original) | No type boundary, and a migration runner to build and test |
| Prisma | A separate schema language, a generated client, and a heavier runtime than four tables justify |
| Kysely | Good type inference, but no migration generation — the second problem stays unsolved |
| Drizzle for both schemas | Two sources of truth for `crawl`. Alembic owns it; see §2 |
