Constraints

One user, one machine, and one failure that matters

Every constraint points away from the usual web-scale crawler architecture.

Constraint Value Consequence
Users One, local only No auth, no multi-tenancy, no horizontal scaling. Do not add them.
Domains 2–3 onboarded at a time, toward ~1,200 Onboarding is the primary interface; crawling is the batch job
Worst failure Being blocked by a site Politeness is a correctness requirement, not etiquette
Sites Bespoke supplier catalogues Thin schema.org coverage; per-domain templates are unavoidable
Cadence Manual, infrequent Throughput barely matters. Correctness and auditability do
Host Mac Studio Ultra Unified memory fits a 30B model, so the model can be good rather than fast
The consequence people miss: at one page every two seconds per host, the per-domain limit is nearly free once the domain count is high. 1,200 domains at a 2 s delay saturates a worker pool long before it troubles any single site. Politeness costs almost nothing here — which is exactly why there is no excuse for skipping it.

The thing that makes this project interesting

The bottleneck is a human, and the arithmetic is brutal

At ~6 domains reviewed per month
~16 years
to reach 1,200 domains

Crawling 1,200 domains is a solved problem that fits on one machine. Approving 1,200 templates is not.

So the engineering effort goes where the constraint actually is:

  • Batch review ships with the review screen, not after it — 20 templates as a grid, approve in one confirm. Retrofitting it later means reworking state management, not adding a view.
  • A sample strip on every review. A selector that works on the page in front of you and fails on the next product is the most common error there is, and it is invisible in a one-page review.
  • Three ways to author a template — a form, a chat, and click-to-select on a rendered page — because the fastest route differs by site and by how much you already know.
  • A coverage report that plots onboarding pace against backlog growth. It is the instrument that says whether any of this worked.
Every feature in this project is judged against that number. If it does not move it, it is decoration.

Principles

Six rules that decided everything else

Each one is a constraint that removed options. They are listed here because every architectural decision later in this deck falls out of one of them.

1 · Politeness is the scheduler, not a setting

A per-domain lock in Postgres, jitter on every delay, Crawl-delay as a floor you cannot configure below. There is no fast mode, because the fast mode is the one that gets you blocked.

2 · The model proposes. It never extracts.

An LLM suggests a CSS selector once per template. A human approves it. During a crawl the model is not running, not reachable, and not in the code path.

3 · Nothing is trusted until it is verified

Every proposal is resolved against the real DOM before a human ever sees it. Confidence comes from a deterministic check, not from the model’s own opinion of itself.

4 · A service owns its data

Two schemas, two roles, enforced by grants. A boundary that is only a convention is a boundary that is already broken.

5 · History is append-only

Templates are versioned, observations are never updated. That is what lets you attribute a price change to the supplier rather than to your own edit three weeks ago.

6 · Boring beats clever

Postgres is the queue. Docker is the deployment. The interesting problem here is review throughput, and spending novelty anywhere else is spending it badly.

Architecture

Six services, two schemas, one model that is not in the crawl path

A service owns its data and nobody else writes it. That boundary is enforced by Postgres grants, not by convention.

The grant is the boundary

The BFF does not proxy

Decision 1 of 5 · ADR-0002

Postgres is the queue. Not Kafka, not Redis.

The claim query is the whole scheduler:

WITH eligible AS (
  SELECT id FROM domains
  WHERE state = 'active'
    AND next_eligible_at <= now()
  ORDER BY next_eligible_at LIMIT 1
)
UPDATE crawl_queue q
SET state = 'in_flight',
    locked_until = now() + '120s'
WHERE q.id = (
  SELECT q2.id FROM crawl_queue q2
  JOIN eligible e ON e.id = q2.domain_id
  WHERE q2.state = 'pending'
  ORDER BY q2.depth, q2.id
  FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING q.*;

Why a broker loses here

  • Dual-write. With a broker the crawled row lands in Postgres and the offset lands in the broker. A crash between them gives duplicate crawls or dropped URLs. SKIP LOCKED makes dequeue-and-write one transaction.
  • Kafka's model fights the requirement. Politeness is per-key rate limiting. Kafka offers ordered partitions and consumer offsets. The domain scheduler would live outside the broker anyway, so the broker contributes nothing to the hard part.
  • Scale does not justify it. Frontier queues exist for crawls spread across many machines.
The hedge, and its price. The queue sits behind a Frontier port. If one node is ever outgrown, that interface is the swap point. One Protocol class — which is the correct cost for an option you do not expect to exercise.
Decision 1 · the queueadr/0002 · specs/002
Expect pushback here from anyone who has run Kafka. The dual-write argument is the one that holds; the scale argument alone sounds like laziness.

Decision 2 of 5 · ADR-0003, ADR-0016

Three worker pools. One politeness gate.

Pool Workers Per host Gated by On a block
Static pages 12 1 concurrent, 2 s gap domains.next_eligible_at pause the domain
Rendered pages 3 in flight 1 concurrent, same gap the same lock pause the domain
Assets 24 5 concurrent, 200 ms gap in-process semaphore pause assets only
Why images may be parallelised within a host and pages may not. A product page is a dynamic request: it hits application code, touches a database, costs the origin real CPU and shows up in their logs as a crawl pattern. An image is a static byte range, usually from a CDN edge. Six concurrent image fetches is ordinary browser behaviour — a real browser opens about that many connections per host to render one page.
One page every two seconds plus bursty asset fetches looks like a visitor. Sequential everything looks like a crawler. The traffic shape is the point, not the request count.
Page politeness lives in Postgres because it must hold across worker replicas and restarts. Asset concurrency is a throughput knob and lives in process — a few extra connections is not a correctness problem.
Decision 2 · concurrencyadr/0003 · specs/002 · specs/008
The asymmetry is counterintuitive and usually lands well — it is a concrete, defensible reason rather than a vibe about being polite.

Decision 3 of 5 · ADR-0004

A block stops the crawler. It is never retried through.

Signal Response
429 / 503 Exponential backoff on that domain, 2×, capped at 15 minutes
403 × 3 Domain auto-paused and raised in the UI. A human decides what happens next
robots.txt Crawl-delay raises the configured delay if higher. It never lowers it
304 A free observation, via stored ETag / If-None-Match

Default delay 2,000 ms, jittered ±30% so request timing is not machine-regular. The User-Agent is real and descriptive, with contact information — pretending to be Chrome is both less honest and, in practice, more likely to be fingerprinted.

A retry loop against a site that has decided to block you is how a temporary block becomes a permanent one. So the default behaviour on a block is to stop and tell someone, which is the opposite of what a crawler usually does.
Stopping is cheap here, which is why it is affordable. A paused domain consumes no crawl budget and sends no requests. A stalled review queue costs nothing operationally — so "block until a human approves" is a cheap guarantee rather than an expensive one.
There is a standing report — requests per domain, 429/403 counts, average effective delay — whose purpose is to be defensible evidence that the crawler behaved. It is the first place to look after a block.

Decision 4 of 5 · ADR-0005

The model proposes selectors. It never extracts values.

rung 1 · free
Structured data
JSON-LD and microdata via extruct. Costs one parse; occasionally eliminates a template entirely.
→
rung 2 · free
Approved selectors
The normal path. Deterministic, versioned, attributable.
→
rung 3 · once per template
Model proposal
Produces a proposal, not data. Goes to a human, never to the database.

rung 4
Unknown queue
Nothing worked. Grouped by root cause so one fix clears dozens. 
// every proposal, before a human sees it
nodes = real_dom.select(selector)
if nodes is empty         → discard 'no_match'
if text(nodes[0]) != claim → discard 'claim_mismatch'
if !many and len(nodes) > 1 → keep, flag 'ambiguous'
else                       → keep, verified
This verification step matters more than the model choice. It converts a probabilistic suggestion into a checked candidate, and it makes a weak proposal fail loudly instead of producing plausible-looking wrong data.
Only rungs 1 and 2 write observations. Which is why an unapproved domain can never generate data, no matter how confident the model was.

Decision 5 of 5 · ADR-0020

Five samples at temperature 0.7 — not one at 0.1

The usual advice for structured output is a greedy decode. It is wrong here, and the reason generalises: sampling diversity is free accuracy whenever a cheap deterministic oracle can rank the samples. One exists — resolve the selector against the real DOM.

A greedy decode gives one answer and no way to tell whether it is good. Five varied answers can be scored: 

score(selector, field) =
  + 40  resolves on every sample URL
  + 25  resolves to the claimed text
  + 15  semantic hook (id, itemprop, data-*, aria-*)
  + 10  cardinality matches intent
  +  5  short (< 4 combinators)
  - 30  uses nth-child / nth-of-type
  - 20  depends on a utility or hashed class
  - 15  resolves on this page only

Two consequences

Merge per field, not per sample

The best price may come from sample 1 and the best images from sample 4. There is no reason to take one model answer whole.

A mixture-of-experts model earns its place

Qwen3-Coder 30B-A3B activates ~3 B parameters per token, which is what makes N=5 affordable. The dense 27B is kept for escalation when no sample clears 60.

Do not calibrate the constants on a laptop model. N, the temperature and the score-60 threshold were chosen for a 30B. On an 8B the scores sit lower, and "fixing" the threshold bakes a laptop constant into the product. Tests assert that ranking works, never that a field clears 60.
Decision 5 · samplingadr/0020 · specs/007
The transferable idea: look for a cheap oracle before reaching for a bigger model. If you can verify, you can sample.

Template authoring · ADR-0019

Three front doors. One pipeline behind them.

Form
Hand-written selectors. Fastest when you already know the site.
Chat
Paste URLs, describe what you want in plain language, watch the draft fill in.
Playground
Click elements on a rendered page.

All three produce the same TemplateDraft and go through the same verify → merge-per-field → rank path. A second verification implementation is a defect regardless of how well it works.

The chat produces a template, never data. Ask it for "the prices on these pages" and you get a verified selector and what it resolves to on each sample — not a table. Returning values would be per-page model extraction through the back door.

Chat authoring. Note the refusal: it cannot start a run and cannot fetch a sixth sample page — and it says so rather than quietly complying. Limits are visible, not hidden.

The visual playground · spec 014

Click-to-select, with no supplier HTML in the page

Supplier pages carry third-party script. An iframe would run it in the app origin; sandbox blocks the script but renders the page wrong; cross-origin framing gives no DOM access anyway — which was the point.

So the sidecar flattens the page into a screenshot plus a geometry list. The browser gets an image and an array of rectangles. 

// cursor → element, in one line of hit-testing
elements
  .filter(e => contains(e.box, x, y))
  .sort((a,b) => area(a.box) - area(b.box))[0]

Smallest containing rectangle is the deepest element. [ / ] walk the ancestor chain via a parent pointer. A click records an example; generalisation runs server-side.

The DOM is still being queried — in Chromium on the server, not in your origin. The screen is a projection of it.

Every match is drawn, not just the clicked one — six boxes where you expected one is instant feedback. Rejected hashed and utility classes are struck through in the ancestry bar.

Playgroundspecs/014
Multi-example is the feature. Clicking the same field on a second sample page eliminates positional steps — a differing nth-of-type index across two examples proves the index is not part of the pattern. The UI asks for the second click rather than waiting for the operator to discover why it matters.

An open problem, if you like this kind of thing

Links hidden behind cascading menus

Case In the fetched HTML What it costs
A — hidden by CSS the <a href> is there, display:none until hover free a parser does not compute styles
B — injected on hover the data is there (inline JSON, a bundle); the links are not small a bounded reveal step, or read the JSON
C — fetched on hover nothing; hovering fires an XHR moderate record the request, do not replay the hover

The risk runs the other way in case A

A mega-menu usually lists the whole category tree on every page. A rule scoped to nav a discovers the entire site at depth 0, defeats the depth cap, and looks like it works until the URL cap halts the domain.

Prefer the path already in the crawl

A menu is usually a shortcut to pages reachable anyway through category tiles and pagination. Run the dry-run with and without the rule: if the projected URL sets match, delete the rule.

An endpoint beats an interaction

If hovering fires /api/nav/children?id=42, the sidecar already has it in the network log. Promote it to a discovery rule — it survives redesigns that rewrite the menu markup.

What is deliberately not being built: a scripted interaction recorder with ordered, nested, conditional steps. Large build, large failure surface, and when a site genuinely needs it the honest answer is usually that it wants an API call rather than a crawl.

Features

What you get, beyond “it crawls pages”

Ten screens, but these are the capabilities behind them.

Authoring

Three ways to make a template

A form, a chat that fetches up to five sample pages, or clicking the element on a screenshot. All three produce the same verified draft.

Review

The sample strip

Every selector is resolved against three to five sibling URLs before you approve. A selector that works on one page and fails on the next is the most common error, and it is invisible in a single-page review.

Review

Batch approval

Twenty templates collapsed to their resolved values, approve or reject per row, one confirm. Same state as the single view, not a second screen.

Discovery

Dry-run before you enqueue

Crawl one listing page and see exactly which URLs would be queued, grouped by the rule that matched. This is where a faceted-navigation trap gets caught at 40 URLs instead of 40,000.

Crawling

Three pools, one gate

Static pages, rendered pages and assets run at different concurrencies but claim the same per-domain lock. A rendered fetch cannot sneak past politeness.

Crawling

Automatic backoff and pause

Three consecutive 403s pause the domain and surface it red at the top of the monitor. A block is never retried through.

Operations

Live run monitor over SSE

Per-domain progress, two throughput lines, asset-queue depth. Reconnects with Last-Event-ID and backfills, so a slept laptop shows a gap, not a stall.

Data

Change attribution

Every observation records the template version that produced it. A price history containing your own selector mistake is otherwise indistinguishable from a real price move.

Data

Standing reports

Extraction health trended by domain and field, broken-template detection over a 20% threshold, price changes filterable by magnitude, crawl-politeness evidence.

Uniqueness

Four things you cannot bolt on afterwards

Verification is the ranking function

Five proposals at temperature 0.7, each resolved against the real DOM, scored deterministically, then merged per field — the winning title can come from sample 2 and the winning price from sample 4. Sampling diversity becomes free accuracy the moment a cheap oracle exists.

The crawl path has no model in it

Not “we cache the model output”. The worker has no LLM client. You can stop llama-server mid-run and nothing changes. That is what makes a million pages cost nothing and replay identically.

Click-to-select with no supplier HTML in the page

The playground is a screenshot plus element geometry, hit-tested in the browser. No iframe, no innerHTML, no “just sanitised” exception — so a supplier page can never execute script in the app document.

The bottleneck is designed for, not hidden

The review screen is the product. Sample strip, batch grid, dry-run discovery and per-field provenance all exist because a human approving ~6 domains a month is the real constraint, and no amount of model quality moves it.

Uniqueness ADR-0020 · ADR-0005 · spec 014

Six services, one origin

How it is put together

browser → edge  Caddy, :8080
            ├── /                   → web     React 19 SPA
            ├── /api/ui/*           → bff     Fastify · owns ui
            └── /api/crawler/*      → api     FastAPI · owns crawl
                                           │
                 worker (crawls, scales) ──┤
                 render (Playwright sidecar)┘
                 db     PostgreSQL 18

+ llama-server on the host — authoring only
A service owns its data and nobody else writes it. Two schemas in one Postgres, enforced by GRANT rather than by convention. The BFF starts a crawl by calling the API, never by inserting a runs row — and an attempted write fails at the database.
  • Caddy, not an API gateway. ~20 lines. A gateway sells auth termination, rate limiting and multi-team routing; there is one user, no auth and one team.
  • SSE bypasses the BFF entirely and needs flush_interval -1. Without it the stream buffers and looks exactly like a frontend bug.
  • Playwright is a sidecar, on its own network with no route to db, api or bff. It fetches arbitrary URLs with a real browser and is the largest attack surface here.
  • Docker-native. Nothing installs on the host except llama-server, which has to be native because Docker on macOS has no Metal passthrough.
A tripwire is written into the plan: re-read the topology ADR at the end of phase 3, and if the BFF turned out to be >80% pass-through, collapse it and move scheduling into Python. Answering that honestly is part of the work.
