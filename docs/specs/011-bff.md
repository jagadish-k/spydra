# 011 — BFF: scheduling, saved views and aggregation

**Phase 3** · Node 26 + Fastify 5 · ADR-0015, ADR-0021

The BFF owns the `ui` schema and three jobs: **scheduling**, **operator
state**, and **screen-shaped aggregation**. It does not proxy the crawler
API, and it is not in the crawl path.

---

## 1. What it owns

```sql
-- ui.schedules — when to crawl. The crawler decides how.
CREATE TABLE ui.schedules (
  id           BIGSERIAL PRIMARY KEY,
  name         TEXT NOT NULL,
  cron         TEXT NOT NULL,              -- 5-field, UTC
  timezone     TEXT NOT NULL DEFAULT 'UTC',
  domain_ids   BIGINT[] NOT NULL,          -- crawl.domains ids; not an FK (§2)
  enabled      BOOLEAN NOT NULL DEFAULT TRUE,
  next_fire_at TIMESTAMPTZ,
  last_fire_at TIMESTAMPTZ,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON ui.schedules (next_fire_at) WHERE enabled;

-- Outcome of each firing. The audit trail for "why did this not run".
CREATE TABLE ui.schedule_fires (
  id          BIGSERIAL PRIMARY KEY,
  schedule_id BIGINT NOT NULL REFERENCES ui.schedules(id) ON DELETE CASCADE,
  fired_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  outcome     TEXT NOT NULL,              -- started|skipped|failed
  run_id      BIGINT,                     -- crawl.runs id, if started
  detail      TEXT
);

-- Saved table views. Filter state already lives in the URL (spec 006);
-- this is for naming one and keeping it.
CREATE TABLE ui.saved_views (
  id         BIGSERIAL PRIMARY KEY,
  screen     TEXT NOT NULL,               -- 'domains'|'products'|'unknown'
  name       TEXT NOT NULL,
  query      JSONB NOT NULL,              -- the URL params
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (screen, name)
);

CREATE TABLE ui.preferences (
  key        TEXT PRIMARY KEY,            -- 'theme'|'row_density'|…
  value      JSONB NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## 2. The boundary

`ui.schedules.domain_ids` references `crawl.domains` but is **not a foreign
key**. That is deliberate: a cross-schema FK would couple the two migration
chains, so dropping a domain in a crawler migration would need a BFF
migration to land first.

The cost is referential drift — a schedule can name a deleted domain. Handle
it where it surfaces: the BFF resolves domain ids against the crawler API
when a schedule fires, drops any that no longer exist, and records
`outcome = 'skipped'` with the detail if none remain. Do not pretend the FK
exists; do not add one.

**The BFF has `SELECT` on `crawl` and no write access at all** (spec 010 §3).
Starting a run is `POST http://api:8000/api/crawler/runs`, never an INSERT.

## 3. Scheduling

A single loop, not a cron library bound to process lifetime:

```
every 30s:
  claim due schedules:
    UPDATE ui.schedules SET next_fire_at = <computed next>
    WHERE enabled AND next_fire_at <= now()
    RETURNING *                                  -- single row lock, one BFF
  for each:
    resolve domain_ids against the crawler API
    POST /api/crawler/runs {domain_ids}
    record ui.schedule_fires
```

**Next-fire is computed and persisted, not held in memory.** A restarted BFF
must not fire everything it missed, and must not forget what is due. The
`UPDATE … RETURNING` is what makes a firing happen once even if the loop
overlaps itself.

Rules:

- **A schedule whose previous run is still active is skipped**, recorded as
  `outcome = 'skipped'`. Overlapping crawls of the same domains would fight
  over the politeness gate and produce two partial runs.
- A missed window — the BFF was down — fires **once** on recovery if it is
  within one interval, otherwise skips to the next. No backfill storms.
- `POST` failure records `outcome = 'failed'` with the problem detail and
  does not retry until the next window. The crawler being down is not
  something to hammer.

## 4. Endpoints

```
GET    /api/ui/schedules
POST   /api/ui/schedules          {name, cron, timezone, domain_ids}
PATCH  /api/ui/schedules/{id}     partial; recomputes next_fire_at
DELETE /api/ui/schedules/{id}
POST   /api/ui/schedules/{id}/run now, out of band
GET    /api/ui/schedules/{id}/fires

GET    /api/ui/views?screen=
POST   /api/ui/views              {screen, name, query}
DELETE /api/ui/views/{id}

GET    /api/ui/preferences
PUT    /api/ui/preferences/{key}

GET    /api/ui/overview           aggregation — §5
GET    /api/ui/healthz
```

Fastify with `@fastify/swagger` and TypeBox schemas, so the BFF publishes its
own OpenAPI document and the SPA generates `schema.ui.d.ts` from it — the
same rule as the crawler API (ADR-0013).

## 5. Aggregation — the part that justifies the tier

`GET /api/ui/overview` backs the Domains screen, which otherwise needs four
round trips: domains, health series, template counts, active run. One call,
one shape:

```json
{ "counts": {"active": 21, "awaiting_review": 7, "broken": 3,
             "paused": 2, "never_crawled": 1, "pages": 18402},
  "domains": [{"id": 14, "host": "northfield-supply.com", "state": "broken",
               "templates": 3, "pages": 1204, "last_crawled_at": "…",
               "health": {"current": 0.41, "series": [0.97,0.96,0.95,0.88,0.62,0.44,0.41]},
               "crawl_delay_ms": 2000, "render_mode": "static"}],
  "active_run": {"id": 412, "state": "running", "started_at": "…"},
  "next_schedule": {"id": 3, "name": "Nightly", "next_fire_at": "…"} }
```

Health comes from a `SELECT` on `crawl`, the schedule from `ui`, the active
run from the crawler API. **This is the BFF doing its actual job** — and if
over time this endpoint is the only one doing real work, re-read ADR-0015 on
collapsing the tier.

## 6. Conventions

- TypeScript strict, same rules as the SPA (`AGENTS.md`).
- **Drizzle for the `ui` schema** (ADR-0021). Schema in
  `bff/src/db/schema/ui.ts`; migrations generated into `bff/drizzle/` by
  `drizzle-kit generate` and applied by `drizzle-kit migrate`.
- **`crawl` types are generated, never hand-written.** `make drizzle-pull`
  introspects into `bff/src/db/schema/crawl.generated.ts`; `make check`
  regenerates and fails on a diff, like `make types`. Alembic owns that
  schema and a hand-written copy would drift from it.
- **`drizzle-kit push` is a defect here.** `generate` + `migrate` only —
  `make migrate-down` is part of the test suite and `push` cannot satisfy it.
- `schemaFilter: ["ui"]` in `drizzle.config.ts`, so a generated migration
  can never contain `crawl` DDL. The Postgres grant is the real boundary;
  this just moves the failure to generate time.
- Raw SQL via Drizzle's `sql` template where the query is the point — the
  `/overview` aggregation, chiefly — with an explicit row type. Same
  principle as ADR-0014 on the Python side.
- Errors use RFC 7807, matching the crawler API, so the SPA has one error
  shape.
- Structured JSON logging to stdout, same fields as the Python services.
- **No business logic about crawling.** If a function in the BFF reasons
  about politeness, templates or extraction, it is in the wrong service.

## 7. Acceptance

- [ ] A schedule due now fires once, even with two loop iterations overlapping.
- [ ] A BFF restarted after downtime fires a missed window once, not N times.
- [ ] A schedule whose domains are mid-run is skipped and recorded as such.
- [ ] `INSERT INTO crawl.runs` from the BFF role is rejected by Postgres.
- [ ] A schedule naming a deleted domain is handled, not crashed on.
- [ ] `/api/ui/overview` returns in one round trip what the Domains screen
      needs, and the screen makes exactly one request.
- [ ] `make types` generates `schema.ui.d.ts` with no `any`.
- [ ] Stopping the BFF mid-run does not affect the run.
- [ ] Every file in `bff/drizzle/` references only `ui.` — asserted by a test.
- [ ] `make check` fails when `crawl.generated.ts` is stale after an Alembic
      migration changes `crawl`.
- [ ] `drizzle-kit migrate` and its down path both run in CI.
- [ ] No committed script or package script invokes `drizzle-kit push`.
